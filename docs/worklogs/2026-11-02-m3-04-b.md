## 实现

| 文件 | 工作 |
| --- | --- |
| worker/execution.py | 可注入 repository/settings/train_fn 的 CPU 编排；UUIDv4/重新验证领取快照、受控数据/哈希/统计、路径与缓存、原 TrainRequest、同源回调、真实产物审计、归属/安全失败/完成写入确认处理 |
| worker/instance_lock.py | LOG_DIR/worker.lock 非阻塞 OS 文件锁；Linux 复用 backend.app.core.worker_lock 公共原语，Windows msvcrt 仅用于 CPU 检查；进程持锁、同进程幂等、退出/强杀释放，不删除活动锁文件 |
| worker/celery_app.py | 保留原配置/任务路由，固定 solo/并发1/预取1、早确认；worker_init 严格拒绝不安全配置或重复实例，worker_shutdown/atexit 释放 |
| worker/__main__.py、scripts/start_worker.sh | 标准启动在 Celery 前持锁，说明锁生命周期；直接 Celery 入口由信号钩子同样保护 |
| worker/tasks.py | 保留 worker.ping；worker.train 只接受 ID，延迟装配 SqlTaskRepository(SessionLocal) 和原 Trainer，返回 task_id/outcome，不自动重试 |
| tests/worker_support.py、test_worker_* | 隔离内存仓储/训练替身、现有合成 CPU bundle、临时真实 SQL/提交故障、OS 子进程与实际 Celery 初始化/CLI 检查 |
| docs/worker.md | 执行语义、单实例/对账交接、生产启动、独立 CPU 与本机 Windows 检查命令、未验收范围 |

Worker 不写 SQL、不复制 Trainer/数据扫描器、不二次写 metrics，也不预先创建 Trainer 独占目录或任务日志。所有生产状态仍由仓储条件更新，Celery SUCCESS 不替代任务业务完成。失去归属后不继续完成/失败写入；完成确认丢失时 get_status，保留有效产物和真实状态，不统一 except 改成 FAILED。

关键证据：

- 正常领取/回调/真实 CPU 审计/complete/重复跳过；eval/重复语义、旧 token、缺文件/篡改/符号链接/缺缓存、保留旧输出与日志、训练和保存失败；未知异常不泄露正文/路径。
- 完成写入前失败保持 RUNNING，写入实际提交但确认丢失可读到 COMPLETED；读取也失败时保持对账状态。无路径删除或 fail 覆盖有效成功。
- 真正用 A 的 SqlTaskRepository 和临时 SQLite 完成执行，失败保留步数；实际 before_commit/after_commit 注入核对确认丢失，而非只断言替身方法参数。

- 子进程被强杀后 OS 锁释放，锁文件仍保留；同进程/信号钩子不重复持锁，释放后的对象不能冒充仍持锁。禁止 GPU/训练库导入的子进程仍能导入生产模块。

## Windows 检查与环境修正记录

本机仅有系统 Python 3.14、无项目 Ubuntu WSL 环境；使用已有运行时 Python 3.12.14，在忽略的 .venv-worker-tools/.venv-worker-tests 中建立独立 CPU 环境，不改原 GPU .venv 或共享依赖。Windows Worker 专项检查通过，两项需要系统符号链接权限的用例明确跳过；完整历史测试有 Linux 链接、POSIX mode、文件关闭和 CRLF 字节差异。用未修改的 d077f84 原始代码副本同样复现此类失败，不修改队友测试/审计器规避。

首次 Linux 快照的 Git archive 继承 Windows autocrlf，将格式样例由 625 字节转换成 628，导致两项原始字节契约失败。改为单次命令 git -c core.autocrlf=false archive 导出原始 Git 内容，未修改实际样例/哈希/全局 Git 配置，随后 301 项与四项 --check 通过。自有 Worker 合成 bundle 也显式保持声明模板 LF 字节，以便 Windows 专项检查，不放宽审计规则。
