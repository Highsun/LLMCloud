## 新增可复现的生产 Worker CPU 冒烟

为核实原有替身检查之外的真实装配，本侧新增 scripts/check_worker_dispatch.py；B 的代码保持原样。隔离目录首轮通过后，将同一脚本加入快进后的 main，并显式覆盖 Celery broker/read/write 环境变量，再复跑通过，避免调用者已有环境变量把消费者指向业务 Broker。

```bash
uv run --locked python scripts/check_worker_dispatch.py
```

需要 redis-server，自动启动私有 Unix socket Redis、临时数据/SQLite、真实 TCP API 和生产 python -m worker。结果后端显式使用隔离内存，不测试生产 Redis 结果存储；业务状态仍从实际 SQLite/HTTP 读取。HF_HOME/HF_HUB_CACHE 指向新的临时空目录，offline=true、CUDA_VISIBLE_DEVICES 为空，保证不访问已有权重、不下载、不执行 GPU。

已实测：

1. HTTP 上传后提交返回 202/QUEUED，实际 Redis 消息由生产 Worker 消费；SQL 被真实领取并结束 FAILED/MODEL_NOT_CACHED，有开始/结束时间，步数仍 0、总步数/进度为 null。
2. 原去重键重放返回 200 和相同失败记录。将原真实 Redis envelope 受控重复投递，生产 Worker 返回 skipped；SQL 内容/时间保持不变，未创建 Trainer 独占产物或任务日志。
3. 实际消费进程持续持有公共 LOG_DIR/worker.lock；受控地对该临时环境作错误的 --services-stopped 声明时，对账 CLI 仍返回 2/instance_lock_busy，无 DB 修改。该反例只针对临时服务，不在实际业务环境谎报停机。
4. 停止本脚本自己的 Worker 和 API 后，同一对账 CLI 可取得锁并返回 current。全部子进程由脚本回收，临时目录删除，不清理任何业务队列。

输出明确为 status=ok、failure_code=MODEL_NOT_CACHED、duplicate_delivery=skipped、live_worker_blocks_reconciliation=true、stopped_services_release_lock=true、gpu_execution_verified=false。该结果证明真实队列的 CPU 失败/幂等/锁链路，未证明成功 GPU 训练或训练中途崩溃恢复。
